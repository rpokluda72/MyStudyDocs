1. Introduction to Docker

Docker (released 2013) is an open-source platform for building, shipping, and running applications inside lightweight, isolated units called containers. A container packages code together with all its dependencies — runtime, libraries, config files — so it runs identically on any machine with Docker installed, eliminating the classic "works on my machine" problem.

Why Containers?

Traditional deployment used Virtual Machines (VMs): each VM ran a full guest OS on top of a hypervisor, consuming gigabytes of disk and minutes to boot. Containers share the host OS kernel — they are milliseconds to start, megabytes in size, and you can run hundreds on a single host.

2. Docker Architecture

Docker uses a client-server architecture. The Docker CLI is the client; it communicates with the Docker Daemon (dockerd) over a Unix socket or REST API. The daemon manages images, containers, networks, and volumes. Internally it delegates to containerd, which uses runc to interface with Linux kernel namespaces and cgroups.

3. Images & Layers

A Docker image is a read-only stack of filesystem layers. Each instruction in a Dockerfile adds one layer on top of the previous. Layers are content-addressed and cached: if a layer has not changed since the last build, Docker reuses the cached version — dramatically speeding up rebuilds.

┌───────────────────────────────────────────────────────────┐

│ IMAGE LAYER MODEL │

│ │

│ ┌───────────────────────────────────────────────────┐ │

│ │ Container Layer (Read/Write) ← your runtime changes│ │

│ ├───────────────────────────────────────────────────┤ │

│ │ Layer 4 — COPY . /app (application code) │ │

│ ├───────────────────────────────────────────────────┤ │

│ │ Layer 3 — RUN npm ci (installed packages) │ │

│ ├───────────────────────────────────────────────────┤ │

│ │ Layer 2 — COPY package*.json /app/ │ │

│ ├───────────────────────────────────────────────────┤ │

│ │ Layer 1 — FROM node:20-alpine (base OS + Node) │ │

│ └───────────────────────────────────────────────────┘ │

│ │

│ Read-only layers are SHARED between containers using │

│ the same image — only the top R/W layer is per-container.│

└───────────────────────────────────────────────────────────┘

Layer Caching Rules

Docker caches every layer. When a layer or its inputs change, that layer and all layers above it are invalidated. Put rarely-changing instructions (base image, tool installs, dependency manifests) near the top and frequently-changing ones (application source code) near the bottom.

Dockerfile instruction Cache behaviour

FROM node:20-alpine ─────────► cached (base image rarely changes)

COPY package*.json ./ ─────────► cached (if package.json unchanged)

RUN npm ci ─────────► CACHED! (reuse node_modules layer)

COPY . . ─────────► MISS (source changes every commit)

RUN npm run build ─────────► re-runs (depends on source)

┌─ TIP ──────────────────────────────────────────────────────────┐

│ Copy dependency manifests BEFORE the full source tree. │

│ npm/mvn/pip install then stays cached across code-only builds.│

└────────────────────────────────────────────────────────────────┘

4. Dockerfile

A Dockerfile is a plain-text build script. `docker build` reads it top-to-bottom, executes each instruction in a temporary container, and snapshots the result as a new read-only layer. The final stack of layers becomes the new image.

Purpose

Example

Example: Node.js Production Dockerfile

A production-ready Dockerfile for a Node.js REST API: dependency caching, non-root user, health check.

# ── production image ──────────────────────────────────────────

FROM node:20-alpine

LABEL maintainer="team@example.com"

WORKDIR /app

# Install dependencies first — maximises cache hit on code-only changes

COPY package*.json ./

RUN npm ci --only=production && npm cache clean --force

# Copy application source

COPY . .

# Drop root privileges

USER node

EXPOSE 3000

HEALTHCHECK --interval=30s --timeout=5s --retries=3

CMD wget -qO- http://localhost:3000/health || exit 1

CMD ["node", "src/server.js"]

Multi-Stage Build

Multi-stage builds use a full build environment (compiler, test runner) in early stages, then copy only the compiled artifact into a small, clean final image. Intermediate stages are discarded — nothing but the JRE and the .jar ships to production.

# ── Stage 1: build with Maven + JDK ──────────────────────────

FROM maven:3.9-eclipse-temurin-21 AS build

WORKDIR /src

COPY pom.xml .

RUN mvn dependency:go-offline -q

COPY src ./src

RUN mvn package -DskipTests

# ── Stage 2: minimal runtime (JRE only) ───────────────────────

FROM eclipse-temurin:21-jre-alpine

WORKDIR /app

COPY --from=build /src/target/*.jar app.jar

USER 1001

EXPOSE 8080

ENTRYPOINT ["java", "-jar", "app.jar"]

Result: final image = JRE + app.jar only. Maven, JDK, and source code never reach the shipped image.

Multi-stage build size comparison

Single stage (JDK + Maven + source) ~700 MB

Multi-stage (JRE + jar only) ~90 MB ← ships to production

6. Networking

Docker provides a pluggable networking model. Each container gets its own network namespace. Containers on the same Docker network can communicate using container or service names as hostnames — Docker runs an embedded DNS resolver. By default containers cannot reach containers on different networks.

Network Drivers

Driver

Description

Use Case

bridge

Default. Private virtual network on host; containers talk by name.

Single-host multi-container apps

host

Container shares host network stack directly. No isolation.

High-throughput / monitoring agents

none

No network access whatsoever.

Batch jobs needing maximum isolation

overlay

Spans multiple Docker hosts; used by Docker Swarm / Kubernetes.

Multi-host orchestration clusters

macvlan

Container gets its own MAC/IP on the physical LAN.

Legacy apps needing direct L2 access

8. Docker Compose

Docker Compose lets you define a multi-container application in a single compose.yml file and manage the entire stack with simple commands. It automatically creates a shared network so every service can reach others by service name.

9. Docker in CI/CD

Docker is the backbone of modern CI/CD. Every build produces a tagged, immutable image; that exact artifact is promoted through staging to production — eliminating "rebuilt on deploy" ambiguity and ensuring what was tested is what ships.

GitHub Actions Workflow

Complete workflow: build, push to GitHub Container Registry (ghcr.io), with layer caching between runs.

# .github/workflows/docker.yml

name: Docker Build & Push

on:

push:

branches: [ main, develop ]

pull_request:

branches: [ main ]

env:

REGISTRY: ghcr.io

IMAGE_NAME: ${{ github.repository }}

jobs:

build-and-push:

runs-on: ubuntu-latest

permissions:

contents: read

packages: write

steps:

- uses: actions/checkout@v4

- name: Log in to Container Registry

uses: docker/login-action@v3

with:

registry: ${{ env.REGISTRY }}

username: ${{ github.actor }}

password: ${{ secrets.GITHUB_TOKEN }}

- name: Extract image metadata (tags, labels)

id: meta

uses: docker/metadata-action@v5

with:

images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}

tags:

type=sha,prefix=

type=ref,event=branch

type=semver,pattern={{version}}

- name: Build and push image

uses: docker/build-push-action@v5

with:

context: .

push: ${{ github.event_name != 'pull_request' }}

tags: ${{ steps.meta.outputs.tags }}

labels: ${{ steps.meta.outputs.labels }}

cache-from: type=gha

cache-to: type=gha,mode=max

CI/CD Best Practices

Practice

Why It Matters

Pin base image versions FROM node:20.14-alpine

Reproducible builds — avoid silent breakage from "latest" changing

Use BuildKit layer cache (type=gha)

CI builds reuse cached layers; minutes saved per run

Tag with Git SHA + semver

Immutable traceability — know exactly what code is in production

Scan images for CVEs (trivy / docker scout)

Catch vulnerabilities before they reach staging or production

Never bake secrets into layers

Secrets in RUN/ENV are visible in docker history — use --secret or env injection at runtime

Use multi-stage builds in CI

Keeps final image tiny; build tools never ship to production

Run tests inside the container

Guarantees tests run against the exact production environment

Sign images (cosign / Docker Content Trust)

Verify image integrity; prevent supply-chain tampering
