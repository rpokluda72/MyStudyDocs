Distributed Event Streaming Platform

1. Introduction to Apache Kafka

Apache Kafka is an open-source distributed event streaming platform originally developed at LinkedIn in 2010–2011 and donated to the Apache Software Foundation. It is designed for high-throughput, fault-tolerant, real-time data streaming at scale.

1.1 What is Apache Kafka?

Kafka is fundamentally a distributed commit log — an append-only, ordered, durable sequence of records. Producers write events to topics, Kafka brokers store them on disk, and consumers read them independently at their own pace. Messages persist for a configurable retention period regardless of whether they have been consumed.

2.2 Topics

A topic is a named category or feed to which messages are published. Topics are multi-subscriber: any number of independent consumer groups can read the same topic without interfering with each other.

  • Identified by a unique string name
  • Split into one or more partitions for parallelism
  • Each partition is an ordered, immutable, append-only log
  • Retention by time (default 7 days) or by size — independent of consumers
  • Compacted topics: retain only the latest value per key (useful for state/cache)

2.3 Partitions and Offsets

Topic Partitions & Offsets

Topic: 'orders' — 3 partitions, replication-factor = 2

Partition 0: [Event_A] → [Event_D] → [Event_G] ...

(Broker 1) offset:0 offset:1 offset:2

Partition 1: [Event_B] → [Event_E] → [Event_H] ...

(Broker 2) offset:0 offset:1 offset:2

Partition 2: [Event_C] → [Event_F] → [Event_I] ...

(Broker 3) offset:0 offset:1 offset:2

Key rules:

• Ordering is guaranteed WITHIN a partition only

• More partitions = more parallelism and throughput

• Each offset is unique within its partition

• Offsets never reset (monotonically increasing)

  • Offset: sequential integer assigned to each message within a partition
  • Consumers commit their offset to track progress
  • Consumers can seek to any offset — replay from beginning or skip to end
  • Offsets are stored in the internal __consumer_offsets topic

2.4 Brokers

A Kafka broker is a server node that stores topic partition data and serves producer/consumer requests. A Kafka cluster is a group of brokers.

3.3 Partitioning Strategies

  • Key-based (default): hash(key) % numPartitions — same key always goes to same partition (ordering guarantee)
  • Round-robin: when key is null — distributes evenly across all partitions
  • Sticky partitioner (Kafka 2.4+): batches null-key records to the same partition within a batch window for efficiency
  • Custom: implement org.apache.kafka.clients.producer.Partitioner interface

3.4 Idempotent Producer & Transactions

Idempotent producer (enable.idempotence=true): Kafka assigns each producer a PID and sequence numbers. Duplicate records caused by retries are automatically detected and discarded.

  • Requires: acks=all, retries > 0, max.in.flight.requests.per.connection <= 5
  • Prevents duplicates on network failures/retries within a single session

Transactions: atomic writes across multiple partitions and topics. Either all writes commit or none do.

  • Set transactional.id on the producer
  • Flow: initTransactions() → beginTransaction() → send() → commitTransaction() or abortTransaction()
  • Consumers must set isolation.level=read_committed to skip uncommitted data

4.4 Rebalancing

When a consumer joins/leaves the group, or new partitions are added, a rebalance redistributes partition assignments across the group.

  • Triggers: consumer join/leave, heartbeat timeout, max.poll.interval.ms exceeded, topic partition count changes
  • Legacy eager rebalance: ALL consumers release ALL partitions, then reassign — brief stop-the-world pause
  • Cooperative incremental rebalance (Kafka 2.4+): only affected partitions are moved; unaffected consumers keep processing
  • session.timeout.ms (default 45s): max time before broker declares consumer dead
  • heartbeat.interval.ms (default 3s): how often consumer sends heartbeat (should be < session.timeout.ms / 3)
  • max.poll.interval.ms (default 5 min): max time between poll() calls; exceed it and the broker removes you from the group

import java.util.*;

import java.time.Duration;

public class OrderConsumer {

public static void main(String[] args) {

props.put("bootstrap.servers", "localhost:9092");

props.put("group.id", "order-processing-group");

props.put("key.deserializer",

props.put("value.deserializer",

"org.apache.kafka.common.serialization.StringDeserializer");

new KafkaConsumer<>(props)) {

consumer.subscribe(List.of("orders"));

while (true) {

ConsumerRecords<String, String> records =

consumer.poll(Duration.ofMillis(100));

for (ConsumerRecord<String, String> rec : records) {

System.out.printf("key=%s val=%s part=%d off=%d%n",

rec.key(), rec.value(), rec.partition(), rec.offset());

if (!records.isEmpty()) consumer.commitSync();

}

5. Replication and Fault Tolerance

Kafka achieves fault tolerance by replicating each partition across multiple brokers. If the leader broker fails, one of the in-sync followers is automatically elected as the new leader.

5.1 Replication Factor

replication.factor defines how many copies of a partition exist. A factor of 3 means 1 leader + 2 follower replicas.

Leader/Follower Replication

Topic 'orders', Partition 0, Replication Factor = 3

Broker 1 -- LEADER (reads & writes) -- [msg0][msg1][msg2][msg3]

Broker 2 -- FOLLOWER (ISR) -- [msg0][msg1][msg2][msg3]

Broker 3 -- FOLLOWER (ISR, lagging) -- [msg0][msg1][msg2]

ISR = { Broker1, Broker2 }

(Broker 3 removed from ISR until it catches up within replica.lag.time.max.ms)

Broker 1 crashes:

→ Controller detects via heartbeat timeout

→ Elects Broker 2 as new leader (it's in ISR)

→ Clients redirect to Broker 2 automatically

→ Broker 3 starts replicating from Broker 2

5.2 ISR (In-Sync Replicas)

Setting

Description

replica.lag.time.max.ms

Max ms a follower can lag behind leader before removed from ISR (default: 30 000)

min.insync.replicas

Min ISR size required for a write to succeed. If ISR < this, producer gets NotEnoughReplicasException

unclean.leader.election.enable

Allow an out-of-sync replica to become leader (risks data loss; default: false)

Best practice: replication.factor=3, min.insync.replicas=2, acks=all. This tolerates 1 broker failure with no data loss.

6. Kafka Streams

Kafka Streams is a Java/Scala client library for building real-time stream processing applications. It runs inside your application — no separate cluster is needed. It reads from Kafka topics, processes the data, and writes results back to Kafka.

6.1 Key Features

  • Embeds in your app — no additional cluster infrastructure
  • Exactly-once processing semantics (EOS)
  • Fault-tolerant stateful processing via local RocksDB + Kafka changelog topics
  • Windowing: tumbling, hopping, session, and sliding windows
  • KStream / KTable / GlobalKTable abstractions
  • Interactive Queries — expose state stores as a queryable service

6.7 Kafka Streams Code Example

Java – Kafka Streams: Filter + Count by Category

Properties props = new Properties();

props.put(StreamsConfig.APPLICATION_ID_CONFIG, "order-processor");

props.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");

props.put(StreamsConfig.DEFAULT_KEY_SERDE_CLASS_CONFIG, Serdes.String().getClass());

props.put(StreamsConfig.DEFAULT_VALUE_SERDE_CLASS_CONFIG, Serdes.String().getClass());

StreamsBuilder builder = new StreamsBuilder();

KStream<String, String> raw = builder.stream("raw-orders");

// Stateless — filter and transform

KStream<String, String> newOrders = raw

.filter((k, v) -> v.contains("NEW"))

.mapValues(v -> v.toUpperCase());

newOrders.to("new-orders");

// Stateful — count per category with 1-minute tumbling window

KTable<Windowed<String>, Long> counts = raw

.selectKey((k, v) -> extractCategory(v))

.groupByKey()

.windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(1)))

.count(Materialized.as("cat-counts-store"));

KafkaStreams streams = new KafkaStreams(builder.build(), props);

streams.start();

Runtime.getRuntime().addShutdownHook(new Thread(streams::close));

8. Schema Registry

The Confluent Schema Registry is a centralized service for managing and enforcing schemas for Kafka messages. It ensures producers and consumers agree on the data format, preventing compatibility issues as schemas evolve.

8.1 Why Schema Registry?

  • Without it: producers and consumers must agree on schema out-of-band (fragile)
  • Provides a single source of truth for message schemas
  • Enforces compatibility rules — prevents breaking changes in production
  • Supports Avro, JSON Schema, and Protocol Buffers (Protobuf)
  • Schema IDs are embedded in message bytes — consumers look up the schema dynamically

8.2 Wire Format and Flow

Producer: Consumer:

1. Create schema (first time) -> 1. Receive message bytes

2. Register with Registry <- 2. Extract magic byte (0x00)

3. Receive schema_id = 42 <- 3. Extract schema_id (4 bytes)

4. Serialize payload with Avro -> 4. Fetch schema from Registry

5. Prepend magic byte + id -> 5. Deserialize payload

Message wire format:

┌──────────┬──────────────────┬──────────────────────────────┐

│ 0x00 │ schema_id (4B) │ Avro / JSON / Protobuf data │

│ (1 byte) │ (big-endian) │ │

└──────────┴──────────────────┴──────────────────────────────┘

magic byte

9.3 KafkaTemplate – Sending Messages

Java – KafkaTemplate Producer Service

@Service

public class OrderProducerService {

@Autowired

private KafkaTemplate<String, OrderEvent> kafkaTemplate;

public void sendOrder(OrderEvent order) {

CompletableFuture<SendResult<String, OrderEvent>> future =

kafkaTemplate.send("orders", order.getOrderId(), order);

future.whenComplete((result, ex) -> {

if (ex == null)

log.info("Sent order {} part {} offset {}",

order.getOrderId(),

result.getRecordMetadata().partition(),

result.getRecordMetadata().offset());

else

log.error("Failed to send order {}", order.getOrderId(), ex);

});

}

}

9.4 @KafkaListener – Consuming Messages

Java – @KafkaListener Consumer

@Component

public class OrderConsumer {

// Single record listener with manual ack

@KafkaListener(topics = "orders", groupId = "order-processor")

public void processOrder(@Payload OrderEvent order,

Acknowledgment ack,

@Header(KafkaHeaders.RECEIVED_PARTITION) int partition,

@Header(KafkaHeaders.OFFSET) long offset) {

try {

processOrderInternal(order);

ack.acknowledge();

} catch (Exception e) {

log.error("Error processing order", e);

}

}

// Batch listener

@KafkaListener(topics = "orders", groupId = "batch-processor",

containerFactory = "batchFactory")

public void processBatch(List<OrderEvent> orders) {

log.info("Batch of {} orders", orders.size());

orders.forEach(this::processOrderInternal);

}

}

9.5 Error Handling with Dead Letter Queue

Java – DefaultErrorHandler + DLQ

@Bean

public ConcurrentKafkaListenerContainerFactory<String, OrderEvent> listenerFactory(

ConsumerFactory<String, OrderEvent> cf,

KafkaTemplate<Object, Object> template) {

ConcurrentKafkaListenerContainerFactory<String, OrderEvent> factory

= new ConcurrentKafkaListenerContainerFactory<>();

factory.setConsumerFactory(cf);

// Retry 3 times with 1s backoff, then publish to .DLT topic

DeadLetterPublishingRecoverer dlqRecoverer =

new DeadLetterPublishingRecoverer(template);

DefaultErrorHandler handler =

new DefaultErrorHandler(dlqRecoverer, new FixedBackOff(1000L, 3));

factory.setCommonErrorHandler(handler);

return factory;

}

12.2 When to Choose Kafka

  • Need to retain and replay event history (audit log, event sourcing)
  • High throughput: millions of events per second
  • Multiple independent consumer groups reading the same data stream
  • Real-time stream processing and analytics pipelines
  • Change Data Capture (CDC) from databases
  • Decoupling microservices in a large distributed system

12.3 When NOT to Choose Kafka

  • Simple task queue with single consumer — RabbitMQ or SQS is simpler and sufficient
  • Request-reply (RPC) patterns — RabbitMQ with temporary reply queues or gRPC is better suited
  • Per-message TTL (time-to-live) required — Kafka retention is log-level only
  • Message priority queuing — Kafka has no native priority support
  • Very small scale with minimal messages — Kafka's operational overhead isn't justified

13. Architectural Patterns with Kafka

13.1 Event Sourcing

All application state changes are stored as an immutable sequence of events in Kafka. Current state is rebuilt by replaying events from the beginning of the log.

Commands Events in Kafka Projections

-------- --------------- -----------

PlaceOrder --> [OrderCreated @ offset 0] --> Orders DB (latest state)

PayOrder --> [OrderPaid @ offset 1] --> Analytics Dashboard

ShipOrder --> [OrderShipped @ offset 2] --> Notification Service

CancelOrder --> [OrderCancelled@ offset 3] --> Audit Log

Kafka IS the source of truth

New consumers can replay from offset 0 to build any read model

Time-travel: seek to any point-in-time snapshot

13.2 CQRS (Command Query Responsibility Segregation)

Commands produce events to Kafka. Read models (projections) are built and maintained by consumers subscribing to those events. Read and write models scale independently.

  • Write side: validates command → produces event to Kafka
  • Read side: consumer subscribes to events → updates denormalized read model (SQL, Elasticsearch, Redis...)
  • Multiple read models can be built from the same event stream independently

13.3 Change Data Capture (CDC) with Debezium

MySQL/Postgres Debezium Kafka Consumers

-------------- -------- ----- ---------

INSERT order --> Source Connector --> mysql.orders --> Elasticsearch

UPDATE order --> (reads binlog/ --> mysql.orders --> Cache Invalidator

DELETE order --> WAL CDC logs) --> mysql.orders --> Data Warehouse

Each row change is published as an event with before/after state

Zero application-code changes required on the source database

13.4 Saga Pattern (Choreography-based)

Order Service --> [OrderCreated] --> Payment Service

|

[PaymentCompleted] --> Inventory Service

|

[StockReserved] --> Shipping Service

|

[ShipmentScheduled] --> Notification

On failure: publish compensating event

e.g. PaymentFailed --> Order Service --> publishes [OrderCancelled]

No central coordinator (orchestrator) needed

Each service only knows about its own events

13.5 Log Aggregation

Application logs are streamed to Kafka via log shippers (Logstash, Filebeat, Fluentd). A central sink consumer writes them to Elasticsearch or a data warehouse for analysis.

13.6 Real-time Analytics Pipeline

Raw Events Kafka Streams / KSQL Output

---------- -------------------- ------

Clickstream --> Filter --> Enrich --> Count --> Dashboard (WebSocket)

IoT Sensors --> Aggregate per device --> Alert System

Transactions --> Fraud detection model --> Block / Approve

No batch delay — results available in milliseconds

14. Best Practices

14.1 Topic Naming and Design

  • Use a hierarchical dot-notation: <domain>.<entity>.<event-type> e.g. shop.orders.created
  • Start with 6-12 partitions; increase later if needed (but you can't decrease)
  • Don't over-partition — each partition is a file handle and memory cost on brokers
  • Use compacted topics for key-based state (latest value per key; never expires by time)
  • Separate command topics from event topics (CQRS)
  • Use dedicated topics for Dead Letter Queues: topic.DLT or topic.error

14.2 Producer Best Practices

  • Production: acks=all + min.insync.replicas=2 + enable.idempotence=true
  • Always use message keys for ordering requirements (same key → same partition)
  • Enable compression (snappy or lz4 for best throughput/CPU balance)
  • Tune batch.size (try 64KB-1MB) and linger.ms (5-50ms) together for throughput
  • Always handle send() failures via callback — never ignore errors silently

14.3 Consumer Best Practices

  • Use manual offset commit (enable.auto.commit=false) for production reliability
  • Keep the poll() loop fast — offload heavy processing to async threads
  • Implement ConsumerRebalanceListener to handle partition revoke/assign cleanly
  • Monitor consumer lag — high lag means consumers can't keep up with producers
  • Use concurrency in Spring Kafka (@KafkaListener + factory.setConcurrency(N))
  • Set max.poll.records to control batch size and prevent timeout on slow processing
