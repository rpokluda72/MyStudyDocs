1. Introduction to Kubernetes

Kubernetes (K8s) is an open-source container orchestration system originally designed by Google (based on their internal Borg system) and donated to the CNCF in 2014. It automates deployment, scaling, self-healing, and networking of containerised applications across a cluster of machines.

Problems Kubernetes Solves

Problem

Kubernetes solution

Manual container placement

Scheduler automatically places pods on nodes with sufficient resources

Container crashes

Self-healing: restarts failed containers, replaces unhealthy pods

Traffic distribution

Services load-balance traffic across all healthy pod replicas

Scaling under load

HorizontalPodAutoscaler scales replicas based on CPU/memory/custom metrics

Service discovery

Built-in DNS: pods reach each other via stable service names

Zero-downtime deployments

Rolling update strategy replaces pods gradually with no downtime

Config & secret management

ConfigMap and Secret objects decouple config from container images

Persistent storage

PersistentVolumes and PVCs abstract storage from pod lifecycle

3. Pods & Workloads

Pod

A Pod is the smallest deployable unit in Kubernetes. It wraps one or more containers that share the same network namespace (same IP, same ports) and can share storage volumes. Pods are ephemeral — if they die, they are replaced, not restarted in place.

# Minimal Pod manifest

apiVersion: v1

kind: Pod

metadata:

name: my-app

labels:

app: my-app

spec:

containers:

- name: app

image: myapp:1.27

ports:

- containerPort: 8080

resources:

requests:

memory: "128Mi"

cpu: "100m" # 100 millicores = 0.1 CPU

limits:

memory: "256Mi"

cpu: "500m"

Deployment

A Deployment is the standard way to run stateless applications. It manages a ReplicaSet to ensure the desired number of identical pod replicas are always running. It handles rolling updates and rollbacks declaratively.

┌────────────────────────────────────────────────────────────────────────┐

│ DEPLOYMENT → ReplicaSet → Pods │

│ │

│ Deployment (desired state: image=myapp:2.0, replicas=3) │

│ └─► ReplicaSet-v2 (ensures 3 pods with image myapp:2.0 running) │

│ ├─► Pod-1 [myapp:2.0] Running │

│ ├─► Pod-2 [myapp:2.0] Running │

│ └─► Pod-3 [myapp:2.0] Running │

│ │

│ On rolling update (myapp:2.0 → myapp:3.0): │

│ Old ReplicaSet-v2 scales DOWN ←──→ New ReplicaSet-v3 scales UP │

│ Old RS kept for rollback (0 replicas but still exists) │

└────────────────────────────────────────────────────────────────────────┘

apiVersion: apps/v1

kind: Deployment

metadata:

name: my-app

namespace: production

spec:

replicas: 3

selector:

matchLabels:

app: my-app # must match template labels

strategy:

type: RollingUpdate

rollingUpdate:

maxSurge: 1 # allow 1 extra pod during update

maxUnavailable: 0 # never have fewer than desired replicas

template:

metadata:

labels:

app: my-app

spec:

containers:

- name: app

image: myapp:2.0

ports:

- containerPort: 8080

resources:

requests:

memory: "256Mi" cpu: "200m"

limits:

memory: "512Mi" cpu: "1000m"

Rolling Update — Step by Step

replicas=3, maxSurge=1, maxUnavailable=0 (update v1.0 → v2.0)

Start: RS-v1 [Pod][Pod][Pod] RS-v2 [ ][ ][ ] total=3

Step 1: RS-v1 [Pod][Pod][Pod] RS-v2 [Pod] total=4 (surge)

Step 2: RS-v1 [Pod][Pod] RS-v2 [Pod][Pod] total=4

Step 3: RS-v1 [Pod] RS-v2 [Pod][Pod][Pod] total=4

Done: RS-v1 [ ] RS-v2 [Pod][Pod][Pod] total=3

RS-v1 kept at 0 replicas for instant rollback:

kubectl rollout undo deployment/my-app → RS-v1 scales back up

4. Services & Ingress

Pods are ephemeral and their IPs change when they are replaced. A Service gives a stable virtual IP and DNS name that load-balances traffic to a dynamic set of pods, selected by label.

Service Types

┌──────────────────────────────────────────────────────────────────────────┐

│ SERVICE TYPES │

│ │

│ ClusterIP (default) ── internal cluster traffic only ───────────────── │

│ Pod-A ──────────────► my-svc:80 (10.96.x.x) ──────► Pod-B, C, D │

│ │

│ NodePort ── exposes on a port on EVERY node (30000-32767) ──────────── │

│ Browser ──► NodeIP:30080 ──► ClusterIP:80 ──────────► Pods │

│ │

│ LoadBalancer ── requests a cloud LB with external IP ───────────────── │

│ Browser ──► 34.x.x.x:80 ──► NodePort ──► ClusterIP ──► Pods │

│ (cloud LB auto-created) │

│ │

│ Ingress ── HTTP/S router, hostname + path based ────────────────────── │

│ Browser ──► ingress:443 ─── /api/* ──► api-svc:80 ──► Pods │

│ (NGINX / Traefik) ─── /* ──► web-svc:80 ──► Pods │

└──────────────────────────────────────────────────────────────────────────┘

# ClusterIP — stable internal virtual IP (default)

apiVersion: v1

kind: Service

metadata:

name: my-app-svc

spec:

selector:

app: my-app # routes to pods with this label

ports:

- port: 80 # port clients connect to

targetPort: 8080 # port on the pod

type: ClusterIP

# LoadBalancer — cloud provider creates external LB automatically

apiVersion: v1

kind: Service

metadata:

name: my-app-lb

spec:

selector:

app: my-app

ports:

- port: 80

targetPort: 8080

type: LoadBalancer

Ingress

Ingress consolidates HTTP(S) routing rules into one object, letting multiple services share a single cloud load-balancer. An Ingress Controller (NGINX, Traefik, AWS ALB) must be installed to act on these rules.

apiVersion: networking.k8s.io/v1

kind: Ingress

metadata:

name: my-app-ingress

annotations:

nginx.ingress.kubernetes.io/ssl-redirect: "true"

spec:

ingressClassName: nginx

tls:

- hosts:

- myapp.example.com

secretName: myapp-tls

rules:

- host: myapp.example.com

http:

paths:

- path: /api

pathType: Prefix

backend:

service:

name: api-svc

port:

number: 80

- path: /

pathType: Prefix

backend:

service:

name: frontend-svc

port:

number: 80

Service DNS

Kubernetes runs an internal DNS server (CoreDNS). Every Service gets a DNS name automatically. Pods within the same namespace can use just the service name; cross-namespace requires the full form.

Same namespace: http://my-app-svc

Cross-namespace: http://my-app-svc.production

Full FQDN: http://my-app-svc.production.svc.cluster.local

Pattern: <service-name>.<namespace>.svc.cluster.local

StatefulSet pod DNS: pod-0.my-svc.production.svc.cluster.local

pod-1.my-svc.production.svc.cluster.local

Service Type Comparison

Type

Accessible from

When to use

ClusterIP

Inside cluster only

Default; pod-to-pod communication (API → DB)

NodePort

Outside via NodeIP:port

Dev/testing; expose without cloud LB

LoadBalancer

Internet via cloud LB IP

Production; single service needing external access

Ingress

Internet via HTTP/HTTPS router

Multiple services on one IP; TLS termination; path routing

ExternalName

Alias to external DNS name

Redirect cluster traffic to an external service (RDS, etc.)

5. Configuration & Secrets

ConfigMaps and Secrets decouple configuration from container images. The same image can run in dev, staging, and prod with different config injected at runtime.

ConfigMap

apiVersion: v1

kind: ConfigMap

metadata:

name: app-config

data:

db-host: mysql.production.svc.cluster.local

db-port: "3306"

log-level: INFO

app.properties: | # multi-line file content

server.port=8080

spring.profiles.active=production

Secret

Secrets store sensitive data. Values must be base64-encoded in YAML (use kubectl create secret for automatic encoding). By default K8s stores Secrets in etcd without encryption — enable Encryption at Rest for production clusters.

apiVersion: v1

kind: Secret

metadata:

name: app-secrets

type: Opaque

data:

db-password: c2VjcmV0MTIz # base64("secret123")

api-key: bXlhcGlrZXk= # base64("myapikey")

# Create without manual base64 encoding:

kubectl create secret generic app-secrets --from-literal=db-password=secret123

Injecting Config into Pods

Both ConfigMaps and Secrets can be injected as environment variables or mounted as files in a volume.

spec:

containers:

- name: app

image: myapp:2.0

env:

# Single key from ConfigMap

- name: DB_HOST

valueFrom:

configMapKeyRef:

name: app-config

key: db-host

# Single key from Secret

- name: DB_PASSWORD

valueFrom:

secretKeyRef:

name: app-secrets

key: db-password

# Mount entire ConfigMap as files in a volume

volumeMounts:

- name: config-vol

mountPath: /etc/config

volumes:

- name: config-vol

configMap:

name: app-config

6. Storage

Pod storage is ephemeral by default — data is lost when the pod is removed. For persistent data (databases, file uploads), Kubernetes uses PersistentVolumes (PV) and PersistentVolumeClaims (PVC).

┌──────────────────────────────────────────────────────────────────────────┐

│ KUBERNETES STORAGE MODEL │

│ │

│ STATIC PROVISIONING: │

│ Admin creates ──► PersistentVolume (50 Gi, AWS EBS disk) │

│ App requests ──► PersistentVolumeClaim ("I need 10 Gi, RWO") │

│ K8s binds PVC to a matching PV automatically │

│ │

│ DYNAMIC PROVISIONING (more common): │

│ App creates PVC with storageClassName: standard │

│ StorageClass provisioner (AWS EBS / GCP PD / Azure Disk) │

│ automatically creates the PV and disk ────────────────────────────── │

│ │

│ Pod ──── volumeMount ──► /var/lib/mysql ──────────► PV (cloud disk) │

│ │

│ PVC lifecycle is independent of Pod lifecycle: │

│ Pod deleted → PVC + data remain; new pod can re-attach same PVC │

└──────────────────────────────────────────────────────────────────────────┘

PersistentVolumeClaim

apiVersion: v1

kind: PersistentVolumeClaim

metadata:

name: mysql-pvc

spec:

accessModes:

- ReadWriteOnce # RWO: one node; RWX: many nodes

storageClassName: standard # triggers dynamic provisioning

resources:

requests:

storage: 10Gi

# Mount PVC in a Deployment:

volumeMounts:

- name: mysql-storage

mountPath: /var/lib/mysql

volumes:

- name: mysql-storage

persistentVolumeClaim:

claimName: mysql-pvc

7. Scaling & Resources

Resource Requests & Limits

Every container should declare resource requests (minimum guaranteed) and limits (maximum allowed). The Scheduler uses requests to place pods on nodes with enough capacity. If a container exceeds its memory limit, it is OOMKilled.

┌──────────────────────────────────────────────────────────────────────────┐

│ RESOURCE REQUESTS vs LIMITS │

│ │

│ requests: what the Scheduler reserves on the node │

│ limits: the ceiling a container can never exceed │

│ │

│ Node capacity: 4 CPU / 8 Gi RAM │

│ ┌──────────────────────────────────────────────────────────────────┐ │

│ │ Pod A: req 1 CPU / 1 Gi │ Pod B: req 1 CPU / 2 Gi │ │

│ │ lim 2 CPU / 2 Gi │ lim 2 CPU / 4 Gi │ │

│ └──────────────────────────────────────────────────────────────────┘ │

│ Scheduled: 2 CPU / 3 Gi reserved (plenty of headroom on this node) │

│ │

│ CPU over limit → throttled (not killed) │

│ Memory over limit → OOMKilled (container restarted) │

│ │

│ CPU units: 1000m = 1 core, 500m = 0.5 core, 100m = 0.1 core │

│ Memory: Mi = mebibytes, Gi = gibibytes │

└──────────────────────────────────────────────────────────────────────────┘

Manual Scaling

# Scale a Deployment to 5 replicas

kubectl scale deployment/my-app --replicas=5

# Or edit the Deployment manifest and kubectl apply

kubectl edit deployment/my-app

HorizontalPodAutoscaler (HPA)

The HPA watches metrics (from metrics-server) and automatically adjusts the replica count to keep average utilization near the target. It scales out when load increases and back in when load drops.

apiVersion: autoscaling/v2

kind: HorizontalPodAutoscaler

metadata:

name: my-app-hpa

spec:

scaleTargetRef:

apiVersion: apps/v1

kind: Deployment

name: my-app

minReplicas: 2

maxReplicas: 10

metrics:

- type: Resource

resource:

name: cpu

target:

type: Utilization

averageUtilization: 70 # scale up when avg CPU > 70%

- type: Resource

resource:

name: memory

target:

type: Utilization

averageUtilization: 80

HPA decision loop (every 15 seconds):

metrics-server collects CPU/memory from every pod

│

▼

HPA controller: desiredReplicas = ceil(currentReplicas × (currentMetric / desiredTarget))

e.g. 3 pods, avg CPU 90%, target 70% → ceil(3 × 90/70) = ceil(3.86) = 4 replicas

│

▼

Deployment updated → Scheduler places new pod → app scales out

Scale-down has a 5-minute cooldown to prevent flapping.

8. Health Checks & Lifecycle

Probe Types

Action on failure

Purpose

Kill container and restart it

Detect deadlocks / hung processes that can't recover

Remove pod from Service endpoints

Don't send traffic to a pod that isn't ready yet

Kill container if not ready within limit

Graceful Shutdown — preStop Hook

When a pod is deleted, Kubernetes sends SIGTERM to the container. The preStop lifecycle hook runs before SIGTERM, letting you complete in-flight requests or drain connections.

lifecycle:

preStop:

exec:

command: ["sh", "-c", "sleep 5"] # finish in-flight requests

terminationGracePeriodSeconds: 30 # SIGKILL after 30s

9. Namespaces & RBAC

Namespaces

Namespaces provide logical isolation within a single cluster. Typical use: one namespace per team or environment (dev, staging, production). Most resource names must be unique within a namespace but can repeat across namespaces.

# Create and switch namespace

kubectl create namespace staging

kubectl config set-context --current --namespace=staging

# Run a command in a specific namespace

kubectl get pods -n production

kubectl get all -n staging

# List all namespaces

kubectl get namespaces

Resource Quotas

ResourceQuotas limit the total resources (CPU, memory, object count) that a namespace may consume, preventing one team from starving others.

apiVersion: v1

kind: ResourceQuota

metadata:

name: team-quota

namespace: team-a

spec:

hard:

pods: "20"

requests.cpu: "4"

requests.memory: 8Gi

limits.cpu: "8"

limits.memory: 16Gi

RBAC — Role-Based Access Control

RBAC controls who can do what in the cluster. Four objects: Role (namespace-scoped permissions), ClusterRole (cluster-wide), RoleBinding (assigns Role to subject), ClusterRoleBinding (assigns ClusterRole globally).

┌──────────────────────────────────────────────────────────────────────────┐

│ RBAC MODEL │

│ │

│ Who? What role? Where? Grants access to... │

│ │

│ ServiceAccount ─► Role ─► namespace ─► specific API resources │

│ User ─► ClusterRole ─► cluster ─► all namespaces │

│ Group ─► ClusterRole via RoleBinding ─► one namespace │

│ │

│ Subject ─────────────► RoleBinding ─────────► Role │

│ (user/group/SA) (the glue) (the permissions) │

└──────────────────────────────────────────────────────────────────────────┘

# Role — namespace-scoped: allow reading pods in "production"

apiVersion: rbac.authorization.k8s.io/v1

kind: Role

metadata:

name: pod-reader

namespace: production

rules:

- apiGroups: [""] # "" = core API group

resources: ["pods", "pods/log"]

verbs: ["get", "watch", "list"]

---

# RoleBinding — bind the Role to a ServiceAccount

apiVersion: rbac.authorization.k8s.io/v1

kind: RoleBinding

metadata:

name: read-pods-binding

namespace: production

subjects:

- kind: ServiceAccount

name: monitoring-sa

namespace: production

roleRef:

kind: Role

name: pod-reader

apiGroup: rbac.authorization.k8s.io

Best Practices

Practice

Detail

Always set resource requests and limits

Without them, pods can starve other pods or be evicted unexpectedly

Use readinessProbe on every container

Prevents traffic to pods not yet warmed up (cache, DB connection pool)

Use livenessProbe carefully

A bad liveness probe can cause a restart loop on a healthy but slow app

Never use "latest" image tag

Pinning to a digest ensures deterministic deploys and rollbacks

One app per Deployment, one Deployment per team

Avoids coupling; each Deployment scales, updates, and rolls back independently

Use namespaces + RBAC for multi-team clusters

Prevents accidental cross-team changes; scope secrets to the right namespace

Declare PodDisruptionBudgets

Prevents K8s from evicting too many pods at once during node maintenance

Use Helm for templated manifests

Avoids duplicating YAML across environments; enables versioned releases

Store manifests in git (GitOps)

Every cluster change is a PR; ArgoCD / Flux syncs git state to the cluster

Enable Network Policies

By default, all pods can talk to all pods — restrict to least-privilege

Set terminationGracePeriodSeconds

Ensure your app has enough time to finish in-flight requests before SIGKILL

Common Interview Questions

Question

Key answer points

What is the difference between a Pod and a Deployment?

Pod = single instance, ephemeral; Deployment = manages many pod replicas, handles rolling updates and self-healing

How does a Service find its pods?

Label selector — Service routes traffic to all pods whose labels match spec.selector

What happens when a pod crashes?

kubelet detects exit, restarts container up to restartPolicy limit; if node fails, controller reschedules pod on another node

What is the difference between ClusterIP and Ingress?

ClusterIP = internal virtual IP; Ingress = HTTP router that sits in front of multiple ClusterIPs, exposes them via one external entry point

How does HPA work?

metrics-server scrapes pod CPU/memory → HPA controller compares to target → adjusts Deployment replicas every 15s

How do you do a zero-downtime deploy?

Rolling update strategy with maxUnavailable=0; readinessProbe ensures new pods are ready before old ones are removed

What is etcd?

Distributed key-value store that holds all cluster state; if etcd is lost, the cluster config is lost — back it up

Difference between ConfigMap and Secret?

Same structure; Secret values are base64-encoded and (optionally) encrypted at rest; Secrets should not appear in logs or image layers
