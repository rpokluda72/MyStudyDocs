Continuous Integration and Continuous Delivery/Deployment

1. Introduction to CI/CD

CI/CD is a set of practices and tooling that automate the journey from a developer's commit to running software in production. The goal is shorter feedback loops, fewer integration surprises, and the confidence to release at any time.

The Problem CI/CD Solves

Without CI/CD, teams integrate code infrequently — often just before a release. This creates "integration hell": weeks of conflicts, bugs that are hard to trace back to a specific change, and slow release cycles. CI/CD solves this by making integration and delivery a continuous, automated process.

WITHOUT CI/CD WITH CI/CD

Dev A codes for 2 weeks Dev A commits daily

Dev B codes for 2 weeks Automated build + tests run in minutes

▼ Bug found immediately after bad commit

MERGE DAY ← integration hell Prod deploy is a routine, boring event

─ conflicts everywhere

─ bugs from 2 weeks ago

─ nobody knows what broke what

─ release delayed by weeks

2. Pipeline Stages

A modern CI/CD pipeline is divided into stages. Each stage has a clear responsibility. Stages run in order — if one fails, later stages are skipped. The principle is fail fast: the cheapest checks run first.

The "Shift Left" Principle

Run the cheapest, fastest checks first. A linting error discovered in 30 seconds costs nothing. The same error discovered after a 20-minute build and deploy wastes everyone's time. Structure pipelines so developers get feedback within 2-3 minutes for the most common failures.

Cost to fix a bug at each stage

Lint (30s) ██ ~$0

Unit test (2min) ████ ~$1

Integration (8min)████████ ~$10

Staging deploy ████████████████ ~$50

Production ████████████████████████████████ ~$1000+

← shift checks leftward → exponential cost savings

3. Deployment Strategies

How you deploy matters as much as whether you deploy. The right strategy balances release speed, risk, and rollback capability. Interviewers commonly ask about the trade-offs between these patterns.

Blue-Green Deployment

Maintain two identical production environments: Blue (live) and Green (idle). Deploy the new version to Green, run smoke tests, then switch traffic. Rollback is instant — just switch traffic back to Blue.

┌──────────────────────────────────────────────────────────────────────┐

│ BLUE-GREEN DEPLOYMENT │

│ │

│ BEFORE: │

│ [Users] ──► [Load Balancer] ──────────────► [Blue v1.0] LIVE │

│ └─────────── [Green v1.0] idle │

│ │

│ DEPLOY: new version goes to Green (no user impact) │

│ [Users] ──► [Load Balancer] ─────────────── [Blue v1.0] idle │

│ └───────────── [Green v2.0] LIVE │

│ │

│ ROLLBACK: switch LB back to Blue — instant, zero downtime │

│ │

│ ✔ Zero-downtime deploy ✔ Instant rollback │

│ ✖ Requires double infra ✖ DB migrations need backward compat. │

└──────────────────────────────────────────────────────────────────────┘

Canary Deployment

Route a small percentage of real traffic (e.g. 5%) to the new version while the majority stays on the old version. Monitor error rates and latency. Gradually increase the percentage if metrics are healthy. Abort and roll back if anything looks wrong.

┌──────────────────────────────────────────────────────────────────────┐

│ CANARY DEPLOYMENT │

│ │

│ PHASE 1 (5% canary) │

│ [Users] ──► [Load Balancer] ──── 95% ──► [Stable v1.0] │

│ └── 5% ──► [Canary v2.0] ← watch │

│ │

│ PHASE 2 (25% if metrics OK) │

│ [Users] ──► [Load Balancer] ──── 75% ──► [Stable v1.0] │

│ └── 25% ──► [Canary v2.0] │

│ │

│ PHASE 3 — 100% (canary becomes the new stable) │

│ │

│ ✔ Real traffic testing ✔ Limits blast radius on bad deploys │

│ ✖ Slower rollout ✖ Needs observability to detect issues │

└──────────────────────────────────────────────────────────────────────┘

Rolling Update

Replace instances of the old version one by one. The load balancer sends traffic only to healthy instances. At any point both old and new versions are live simultaneously.

┌──────────────────────────────────────────────────────────────────────┐

│ ROLLING UPDATE │

│ │

│ Start: [v1] [v1] [v1] [v1] all instances on v1.0 │

│ │

│ Step 1: [v2] [v1] [v1] [v1] drain + replace instance 1 │

│ Step 2: [v2] [v2] [v1] [v1] replace instance 2 │

│ Step 3: [v2] [v2] [v2] [v1] replace instance 3 │

│ Done: [v2] [v2] [v2] [v2] all on v2.0 │

│ │

│ ✔ No extra infra needed ✔ Zero downtime │

│ ✖ Both versions live at once ✖ Slow rollback (must roll forward) │

│ ✖ Requires API backward compat between v1 and v2 │

└──────────────────────────────────────────────────────────────────────┘

Feature Flags (Feature Toggles)

Deploy code to production with new features hidden behind a runtime flag. The feature can be toggled on/off without a new deployment — per user, per group, or globally. Decouples deploy from release.

┌──────────────────────────────────────────────────────────────────────┐

│ FEATURE FLAGS │

│ │

│ Code deployed to prod: │

│ if (featureFlags.isEnabled("new-checkout", userId)) { │

│ showNewCheckout(); ← new code, hidden by flag │

│ } else { │

│ showOldCheckout(); ← old code, still running │

│ } │

│ │

│ Flag OFF → all users see old behavior (safe default) │

│ Flag ON → 10% of beta users see new feature → monitor │

│ Flag ON → 100% — new feature is "released" │

│ │

│ ✔ Decouple deploy from release ✔ Easy A/B testing │

│ ✔ Kill switch for bad features ✖ Code complexity (tech debt) │

└──────────────────────────────────────────────────────────────────────┘

4. GitHub Actions Fundamentals

GitHub Actions is GitHub's built-in CI/CD platform. Workflows are defined as YAML files stored inside the repository. Each push, pull request, or scheduled timer can trigger one or more workflows automatically.

Core Concepts

Concept

Description

Workflow

YAML file in .github/workflows/ — one or more jobs triggered by events

Event

What triggers the workflow: push, pull_request, schedule, workflow_dispatch, etc.

Job

A set of steps that run on the same runner; jobs run in parallel by default

Step

A single task inside a job: either uses: (an action) or run: (a shell command)

Action

Reusable, pre-packaged unit of work (e.g. actions/checkout, docker/build-push-action)

Runner

Virtual machine that executes the job (GitHub-hosted: ubuntu, windows, macos)

Artifact

File produced by a job and optionally uploaded to share with downstream jobs

Context

Objects that expose data: github, secrets, env, steps, needs, runner, inputs

Expression

${{ ... }} — evaluate context values, operators, and functions inside workflow YAML

Concurrency Control

The concurrency: key ensures only one run of a workflow (or group) executes at a time. Useful to prevent parallel deploys to the same environment.

# Cancel in-progress runs for the same branch on new push

concurrency:

group: ${{ github.workflow }}-${{ github.ref }}

cancel-in-progress: true

6. Jobs, Steps & Matrix Builds

Job Dependencies — needs:

Jobs run in parallel by default. Use needs: to declare that a job must wait for another to succeed first. This models the pipeline's stage order.

jobs:

lint:

runs-on: ubuntu-latest

steps:

- uses: actions/checkout@v4

- run: npm run lint

test:

needs: lint # waits for lint

runs-on: ubuntu-latest

steps:

- uses: actions/checkout@v4

- run: npm test

deploy:

needs: [ lint, test ] # waits for BOTH

runs-on: ubuntu-latest

steps:

- run: echo "deploying..."

Job dependency graph:

lint ──┐

├──► deploy

test ──┘

lint and test run in PARALLEL; deploy waits for both.

Conditional Execution — if:

Steps and jobs can be guarded by if: expressions. Common use: run deploy only on main branch, or send notifications only on failure.

jobs:

deploy:

# only run this job on pushes to main (not on PRs)

if: github.ref == 'refs/heads/main'

runs-on: ubuntu-latest

steps:

- name: Deploy

run: ./deploy.sh

- name: Notify on failure

# always() ensures this step runs even if previous steps failed

if: failure()

run: echo "Deploy failed — alert team"

Matrix Strategy

A matrix builds creates multiple parallel job instances from combinations of variables. Common use: test against multiple language versions or operating systems.

jobs:

test:

runs-on: ${{ matrix.os }}

strategy:

fail-fast: false # do not cancel others if one fails

matrix:

os: [ ubuntu-latest, windows-latest ]

node-version: [ 18, 20, 22 ]

steps:

- uses: actions/checkout@v4

- uses: actions/setup-node@v4

with:

node-version: ${{ matrix.node-version }}

cache: 'npm'

- run: npm ci && npm test

This matrix produces 2 × 3 = 6 parallel jobs: every combination of OS and Node version.

Caching Dependencies

The actions/cache action saves and restores directories between runs. Without caching, npm install or mvn download runs in full on every job — wasting minutes per build.

- name: Cache Maven packages

uses: actions/cache@v4

with:

path: ~/.m2/repository

key: ${{ runner.os }}-maven-${{ hashFiles("**/pom.xml") }}

restore-keys: |

${{ runner.os }}-maven-

# setup-node and setup-java both have a built-in cache: option:

- uses: actions/setup-node@v4

with:

node-version: "20"

cache: 'npm' # shorthand for npm ci cache

Passing Data Between Jobs — outputs & artifacts

jobs:

build:

runs-on: ubuntu-latest

outputs:

version: ${{ steps.ver.outputs.tag }}

steps:

- id: ver

run: echo "tag=$(git describe --tags)" >> $GITHUB_OUTPUT

- run: npm run build

- uses: actions/upload-artifact@v4

with:

name: dist

path: dist/

deploy:

needs: build

runs-on: ubuntu-latest

steps:

- uses: actions/download-artifact@v4

with:

name: dist

- run: echo "Deploying version ${{ needs.build.outputs.version }}"

OIDC — No Long-Lived Credentials

OpenID Connect (OIDC) lets GitHub Actions authenticate to cloud providers (AWS, GCP, Azure) without storing long-lived credentials as secrets. GitHub issues a short-lived JWT token per workflow run; the cloud provider exchanges it for a scoped access token.

WITHOUT OIDC WITH OIDC

AWS_ACCESS_KEY_ID stored in GitHub exchanges JWT with AWS STS

GitHub Secrets — lives forever, for a 15-min scoped token.

must be rotated manually, No static credential stored anywhere.

blast radius if leaked is huge.

steps:

- uses: aws-actions/configure-aws-credentials@v4

with:

role-to-assume: arn:aws:iam::123456789:role/GitHubActions

aws-region: eu-west-1

# From here all aws CLI calls use the short-lived session token

Environments & Protection Rules

GitHub Environments (Settings → Environments) add protection rules to deployment jobs: required reviewers, wait timers, and IP allow-lists. A job that targets an environment is paused until the rules pass.

jobs:

deploy-prod:

needs: deploy-staging

environment:

name: production # must match name in GitHub Settings

url: https://myapp.com

runs-on: ubuntu-latest

steps:

- run: ./deploy.sh production

# GitHub will pause this job and wait for a required reviewer to approve

# Secrets scoped to "production" environment are only available here

8. Reusable Workflows & Composite Actions

As CI/CD matures, teams need to share pipeline logic across repositories without copy-pasting YAML. GitHub Actions offers two mechanisms: reusable workflows and composite actions.

Reusable Workflow — workflow_call

A workflow that uses on: workflow_call: can be called from another workflow using uses:. It encapsulates an entire job graph and can accept typed inputs and secrets.

# .github/workflows/docker-build.yml (the reusable workflow)

on:

workflow_call:

inputs:

image-name:

required: true

type: string

secrets:

registry-token:

required: true

jobs:

build-push:

runs-on: ubuntu-latest

steps:

- uses: actions/checkout@v4

- uses: docker/build-push-action@v5

with:

push: true

tags: ${{ inputs.image-name }}:${{ github.sha }}

# .github/workflows/ci.yml (caller workflow)

jobs:

docker:

uses: myorg/shared-workflows/.github/workflows/docker-build.yml@main

with:

image-name: ghcr.io/myorg/myapp

secrets:

registry-token: ${{ secrets.GHCR_TOKEN }}

Composite Action

A composite action bundles multiple steps into a single reusable action.yml. Unlike a reusable workflow, a composite action runs inside an existing job — useful for shared setup logic across many workflows.

# .github/actions/setup-java-maven/action.yml

name: 'Setup Java + Maven cache'

description: 'Setup JDK 21 with Maven dep cache'

inputs:

java-version:

default: '21'

runs:

using: 'composite'

steps:

- uses: actions/setup-java@v4

with:

java-version: ${{ inputs.java-version }}

distribution: temurin

cache: maven

# usage in any workflow:

- uses: ./.github/actions/setup-java-maven

Cancel stale in-progress runs on the same branch to save runner minutes

Pin action versions to a SHA

uses: actions/checkout@11bd71901... — immune to tag re-pointing attacks

Use environments for promotions

Staging → prod gate with required reviewers; secrets scoped to environment

Store secrets at the right scope

Org secrets for shared keys; env secrets for prod-only credentials; never in code

Prefer OIDC over static credentials

No long-lived keys stored in GitHub Secrets; automatic rotation per run

Tag images with git SHA, not "latest"

"latest" is mutable; SHA is immutable traceability — know exactly what is running

Add status badges to README

README badges give immediate visibility into pipeline health

Keep workflow YAML DRY

Extract repeated setup into composite actions or reusable workflows

Security Best Practices

Risk

Mitigation

Script injection via github.event.*

Never interpolate user-controlled values directly in run:; use env: variables instead

Overly broad GITHUB_TOKEN perms

Set permissions: at workflow or job level; grant only what is needed (contents: read)

Untrusted actions in uses:

Pin to a commit SHA; review source before using third-party actions

Secrets visible in logs

Never echo secrets; GitHub masks known values but won't mask derived strings

pull_request_target abuse

Never checkout and run PR code in pull_request_target without sanitizing inputs

Forked PR with secrets access

Secrets are NOT available to fork PRs by default — keep it that way
